## 세 단계의 "왜 하는지" — 공식 사유로 교체 (26-09-02 제공)

내가 쓰던 ①단 이득(`1-1, 1-2처럼 잘게 나뉜 문항도 경계가 확실해져요`)은 **폐기**.
진짜 이유는 **학생이 활동지에 해 놓은 낙서·메모를 AI가 문제 지시문으로 오독하는 걸 막는 것**이다.

| 단계 | 왜 하는지 (근거 원문) |
|---|---|
| ① 빈 활동지·문항 확정 | 문항 지시문을 미리 확정해 두면, 학생 제출물의 낙서·메모로 훼손된 지시문을 AI가 오독하는 것을 막는다 |
| ② 채점기준 연결 | 각 문항에 요구되는 채점기준만 적용해 평가한다 |
| ③ 모범답안·채점 가이드 | 선생님이 생각하는 "상" 수준을 AI가 파악해, 추론이 불가능한 답안도 채점할 수 있다 / 채점 가이드로 선생님의 채점 고려 사항을 반영한다 |

①단은 두 안 중 **1안(낙서·메모 오독)** 을 골랐다 — 2안("답안에 더 집중")은 무엇이 좋아지는지가
흐려 행동 유도가 안 된다. 2안으로 바꾸려면 `ADV_WHY[1]`·`ADV_GAIN[1]`·`ADV_LOAD.ws.why` 세 줄.

**같은 이득을 세 시점에 반복**한다 — 기다릴 때(`ADV_LOAD.why`) · 하는 동안(`ADV_WHY`, 탭 아래 상시) ·
마쳤을 때(`ADV_GAIN`, 1회). 과업이 무거워 한 군데서만 말하면 놓친다.
바깥 문구 두 곳(저장 직후 분기 팝업 · 설계 상세 고도화 카드)도 같은 말로 맞췄다.
업계어는 풀었다 — `훼손된 지시문 오독` → `낙서나 메모를 문제로 잘못 읽음`,
`"상" 기준 수준` → `잘한 답안의 수준`, `추론 불가능한 답안` → `미루어 짐작하기 어려운 답안`.

## ▶ 이어받기

AI팀이 **루브릭 검토 API를 실제로 만들었다**(맥 쪽 목업: `루브릭 AI 검토 목업` 아티팩트).
v8 설계 상세의 `채점기준` 섹션에 그 기능을 붙였다.

```
채점기준                      채점기준 5개 · 만점 25점
어떻게 입력해야 하나요?  채점기준 입력 예시   ← 쓰기 전에 필요한 도움말
채점기준 카드들 (짚힌 카드는 머리 아래 코멘트)
[✨ 채점기준 AI 생성] [+ 직접 추가]           ← 만드는 일
─────────────────────────────────────       ← 단을 가름
[ AI 검토 밴드 ]                              ← 다 쓴 뒤에 하는 일
```

**단을 가른 이유** — `AI 생성`·`직접 추가`는 *추가하는* 행위, `AI 검토`는 *다 쓴 뒤 점검하는*
행위다. 셋을 한 줄에 두면 검토가 "세 번째 추가 방법"으로 읽힌다.

**HowToUse를 카드 위로 올린 이유(09-02 올립 지적)** — 개발 화면은 이 줄이 섹션 **맨 아래**였다.
거기에 검토 밴드가 들어오면서 바닥이 `추가 / 도움말 / 검토` 세 덩이가 되어 짝이 안 보였고,
쓰기 전에 필요한 도움말인데 카드 5개를 지나야 보였다. 카드 앞으로 올려 바닥을 두 덩이로 만들었다.
⚠️ **개발 확정 화면과 다른 유일한 지점** — 개발 전달 시 짚을 것.

## 무엇을 짚는가 (API 계약)

AI팀 목업의 `issue_type` 두 가지를 그대로 쓴다. 화면 문구는 업계어를 걷어냈다.

| API | 화면 문구 | 제안 필드 |
|---|---|---|
| `overloaded_element` | 한 기준에 여러 가지가 섞여 있어요 | `suggestion.split_into[]` → 칩 |
| `ambiguous_boundary` | 배점 사이 경계가 흐릿해요 | `suggestion.revised_descriptions[]` → 전/후 |

응답 예(AI팀 목업 `기대 출력 JSON`):
```json
{"comments":[{"element_id":910002,"element":"표현","issue_type":"overloaded_element",
  "target_level_ids":[],"comment":"…","suggestion":{"split_into":["어법의 정확성","어휘 사용","분량"]}}]}
```

## 목업의 판정은 **진짜로 돈다** (하드코딩 아님)

올립 요구 = "실제로 사용자가 해보게 하고 싶다". 그래서 씨앗 데이터에 결과를 박지 않고
현재 입력된 채점기준 텍스트를 훑는 규칙을 넣었다 — 교사가 직접 고쳐 쓰면 판정이 따라 바뀐다.

- **섞임**: `RV_AXES` 8개 평가 축(어법/어휘/문장/분량/구성/근거/주장/기한) 중 **셋 이상**이
  한 기준에 잡히면 → 그 축들을 `split_into`로 제안
- **경계**: 세부 기준 문장에 정도 부사(`다소·대체로·매우·약간·조금·어느 정도·상당히`)가 있으면
- 한 기준에 **코멘트 하나**, 섞임이 우선(쪼개는 게 먼저다)

**고쳐 쓴 문장은 지어내지 않는다.** `RV_FIX`에 미리 적어 둔 줄만 전/후를 보여 주고,
교사가 직접 쓴 줄은 짚기만 한다 — [시스템이 아는 것만 표시] 원칙.

씨앗(`RUBRIC_SEED`, 논설문 5개)에 그대로 돌리면 **2건**이 나온다.
가짜 채점기준을 새로 끼우지 않고 원래 있던 것에서 걸린 것이다.

| | 걸린 이유 |
|---|---|
| 채점기준 2 (논리적 구성) | `연결이 **다소** 어색함` → 경계 흐릿 |
| 채점기준 3 (어휘·문장 표현) | 어법 + 어휘 + 문장 표현 3축 → 섞임 |

## 드로워 = 채점기준 전체를 고치는 작업대 (26-09-02 올립 지시, 2번 되물림)

**1차: 카드 안 인라인 코멘트 → 되물림**
> "저 수정한 안내 사항 거슬리는데 고쳐도 계속 남아있으니까 별로야"

카드 안에 상자를 두면 **고치는 내내 자리를 차지하고 배점 표를 아래로 민다.**

**2차: 읽기 전용 드로워 → 되물림**
> "나는 채점기준 전체 표시해주고 고칠것은 드로워내에서 고친다음 덮어쓰게 하는 게 나을거같은데"

읽는 곳과 고치는 곳이 갈라져 있으면 **닫고 → 카드 찾고 → 다시 타이핑**이다.

**3차(현행): 우측 드로워에 채점기준 전체를 펴고, 거기서 고쳐 덮어쓴다.**
v2·v3의 `채점기준 AI 생성` 드로워와 **같은 규격**
(overlay `rgba(0,0,0,.35)` · 우측 800px · 헤더 18px/700 + X · 스크롤 바디 24px · 푸터 border-top).

- **짚힌 것만이 아니라 5개 전부** 편집 가능 — 옆 기준을 보며 고쳐야 결이 맞는다
- 짚힌 기준은 `1.5px 주황 테두리` + 그 안 맨 위에 AI 코멘트(하늘색). 배지는 안 단다(코멘트 제목과 같은 말)
- **제안 문장은 그 배점 줄 바로 아래**에 `✨ 이렇게 … [적용]` — 멀리 두면 어느 줄 얘기인지 모른다
- 800px이라 제목을 표 옆이 아니라 **위에 쌓았다** — 고치는 건 세부 기준 문장이라 폭을 다 준다
- **복사본(`DW_R`)을 고친다.** `채점기준에 반영`을 눌러야 진짜가 바뀌고,
  안 누르고 닫으면 `고친 내용 버리기` 확인. 카드에서 고칠 때와 같은 연쇄가 걸린다
  (문항 연결 stale · 채점 후면 저장 시 초기화 확인 · 검토 결과 무효화)
- **`적용`은 AI가 고쳐 주는 게 아니다** — API가 이미 돌려준 `revised_descriptions`를
  선생님이 필드에 넣는 것. 넣고 나서 더 고쳐도 된다.
  누르면 **제안 줄은 사라진다** — 필드가 바뀐 걸 눈으로 보는데 "적용됨"을 또 말하면 자리만 차지

## 두 지적은 성질이 다르다 — 고치기 vs 늘리기 (26-09-02 올립)

> "기존 있는 걸 삭제하는 건 OK, 없는 걸 새로 추가하게 하는 거가 고민이거든"

| | 경계 흐릿 | 섞임 |
|---|---|---|
| 고치는 방식 | 기존 문장 **교체** | 채점기준을 **늘림** |
| API가 주는 것 | `revised_descriptions` — 완성된 문장 | `split_into` — **축 이름뿐** |
| 만점 | 안 변함 | **변함** → 채점 결과 무효 |
| AI가 지어내나 | 아니오 | **예**(문장 9줄·배점 배분) |

섞임을 자동화하려면 AI가 축마다 세부 기준을 새로 쓰고 20점을 7/7/6으로 쪼개야 한다.
**API에 없고, 배점 배분은 교사의 평가 의도**다.

→ **"없는 걸 만들기"를 "있는 걸 복사하기"로 바꿔 푼다.**
드로워 채점기준 머리에 **`복제`·`삭제`를 카드와 똑같이** 둔다. 섞임 코멘트는 안내 문장만
(같은 상자 두 줄 위에 버튼이 있어 중복). 원본의 사본이 바로 아래 생기고, 교사가 각각 하나씩만 남긴다.
**시스템이 지어내는 게 0**이고, 만점이 늘어난 건 토스트와 총점 표시로 바로 보인다.
사본에는 코멘트가 안 붙는다 — AI가 판정한 건 원본이니까.

**삭제도 복사본에만 든다.** 카드의 삭제는 "되돌릴 수 없습니다"지만 드로워는
`채점기준에 반영`을 눌러야 진짜로 지워지므로 그렇게 말하지 않는다 — 버리고 닫으면 그대로다.
코멘트 본문에서 **채점기준 번호를 뺐다**(`이 기준이 …`) — 복제·삭제로 순번이 밀리면 틀리기 때문.

기각한 길 둘 — **빈 채점기준 N개 생성**은 배점이 비어 설계가 미완성으로 잠기고 빈칸 9개를 던진다.
**AI가 다 써 주기**는 API에 없는 걸 목업에서 지어내는 것이라 [[feedback_system_honest_signaling]] 위반.

## 밴드는 **한 모습만** 쓴다 (26-09-02 올립, 두 번에 걸쳐 줄임)

> "여기 배너는 상태에 따라 계속 달라지는 게 아니라 하나로 처리하면 어때?
> 쓰려면 쓰고 말려면 마는 기능인데 넘 복잡도 높이는 거 같아서"

처음엔 4가지 얼굴이었다 — 파랑 권유 / 주황 `n곳 짚음`+점프 칩 / 초록 통과 / 파랑 stale.
**선택 기능인데 읽는 비용이 기능값보다 커졌다.** 하나로 고정했다.

```
✨ AI가 헷갈릴 만한 곳을 미리 짚어 드려요
   한 기준에 여러 가지가 섞여 있거나 배점 사이 경계가 흐릿하면 알려 드려요.
   그런 곳을 먼저 고쳐 두면 AI가 매기는 점수가 선생님 기준에 더 가까워져요.
   [ 채점기준 AI 검토 ]
```

- 검토 전·후·통과·고친 뒤 **전부 같은 문구**. 조건부는 잠금 사유 한 줄뿐
  (`채점기준을 다 입력하면 검토할 수 있어요` + 버튼 비활성), 채점기준 0개면 숨김
- **결과가 아직 살아 있으면 다시 돌리지 않고 바로 연다** — 버튼이 하나라도 5초를 또
  기다릴 이유는 없다. 채점기준을 고치면 `rvInvalidate`가 치워 주므로 늘 최신
- 결과가 어땠는지는 **드로워/검토 화면이** 말하고, 짚힌 곳은 **카드 주황 테두리**로 남는다.
  밴드는 '들어가는 문'일 뿐
- 함께 걷어낸 것 — 카드로 점프하는 칩(고치는 곳이 카드가 아니라 드로워라 갈 일이 없다),
  `rvJump`·깜빡임 CSS, `.rv-box.rv-ok`/`.rv-hit` 색 규칙, `S.reviewRan`

로딩 중에는 밴드를 비운다(스피너는 드로워/검토 화면이 돌린다).

검토를 누르면 **드로워가 먼저 열리고 그 안에서 돈다** — 결과가 나올 자리에서 기다리게.

- **채점기준 미입력이면 버튼 비활성** + 잠금 사유를 버튼 **앞**에
- **막지 않는다** — "그대로 둘 수도 있어요, 채점은 막지 않아요"
- **고치면 결과가 사라진다** — 검토는 그때 그 문장을 본 결과라, 채점기준을 건드리면
  코멘트를 걷고 `채점기준이 바뀌었어요 / 다시 검토해 보세요`로 되돌아간다.
  입력 중에는 카드를 다시 그리지 않고(커서가 튄다) 붙어 있던 것만 DOM에서 걷어낸다
